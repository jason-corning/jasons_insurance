Method

Steps performed

Reviewed the three instruction sources

Used the Forethought Help Center as product instruction, the Drive file Implementation Onboarding Packet as the onboarding guide, and the Drive file Autoflow as the policy-writing example. Extracted the recurring practices: state a clear goal, ask only for missing information, reuse known context, confirm before a mutation, call a named action, handle failures safely, and test before publish.

Mapped the insurance journeys and API boundary

Reviewed the live API documentation, FAQs, help articles, plan search, broker search, account recovery, enrollment, and profile routes. Classified each workflow as public, recovery, knowledge, or authenticated mutation.

Created reusable context variables

Added reusable non-secret values for enrollment ID, plan ID, date of birth, member count, plan type/tier/budget, broker ZIP/query/specialty, cancellation reason, mailing address, and communication-preference flags. Passwords, reset tokens, one-time codes, payment data, access tokens, and cookies were deliberately excluded.

Created and tested six reusable API actions

  • List Insurance Plans → /api/plans/
  • Search Brokers → /api/brokers/
  • Search Insurance FAQs → /api/faqs
  • List Insurance Help Articles → /api/help/articles/
  • Recover Insurance Username → /api/auth/forgot-username
  • Request Password Reset → /api/auth/forgot-password

Authored one policy per customer outcome

Created 11 separate Agent Builder drafts. Each policy has one outcome, collects only missing data, reuses context, confirms irreversible changes, avoids unsupported claims, and includes failure/handoff behavior. Public and recovery flows use named reusable actions; authenticated mutations currently route to the secure website instead of requesting a cookie.

Embedded reusable actions where they are safe

Embedded the password-reset, username-recovery, plan-list, FAQ/help-article, and broker-search actions in their corresponding Autoflows. Authenticated enrollment/profile actions were not created with a copied browser cookie because that would expose a session credential and would not represent user-specific authorization correctly.

Renamed every draft for concise customer language

Changed all 11 display names in the live tenant and verified every final name by exact search. The table below records the before/after mapping.

Added eight training phrases to every Autoflow

Followed Forethought's training-phrase best practices and the Agent Builder creation guide: keep one clear goal, use 5–15 natural customer phrases, cover meaningful wording variations, and avoid deliberate misspellings. Added 88 phrases total and verified exactly eight saved phrases on each draft.

Kept every Autoflow unpublished

Verified all 11 drafts remain Off. No Publish action was taken. The existing live Fallback agent was not changed.

Compared the tenant with the Help Center

Captured tenant and Help Center screenshots, linked canonical articles, and documented 10 terminology, navigation, type-support, versioning, and OAuth-insertion discrepancies in the companion local HTML log.

Authentication review

Safe path documented; provider configuration still required

The official article Enable OAuth Sign-In for Solve Widget Conversations requires OAuth 2.0 Authorization Code Flow. It says credentials are never shared with Forethought, the access token persists only for the conversation session, and configured API actions use that token.

What the tenant supports

  • Action Builder → Authentication → Create new authentication.
  • Required fields: Name, Client ID, Client Secret, Auth URL, Token URL, authentication type, and optional scope.
  • The Autoflow Actions drawer exposes an OAuth Sign In action even though the article's insertion step only describes a Classic workflow.

Why no fake client was created

The live insurance site currently uses an httpOnly ji_session cookie and does not expose OAuth authorization and token endpoints. Creating an Authentication Client with invented endpoints or copied cookies would be nonfunctional and unsafe.

Inputs needed to finish authenticated execution

  1. Deploy a real OAuth 2.0 Authorization Code provider for Jason's Insurance, or identify the existing provider.
  2. Provide its Client ID and Client Secret through the tenant's secure Authentication Client form—not context variables.
  3. Whitelist https://app.forethought.ai/solve/auth/oauth as the redirect URL.
  4. Create OAuth-authorized API actions for cancel, reinstate, address, phone, and preferences.
  5. Add OAuth Sign In before each sensitive action, test with live credentials, verify failure paths, and keep the flows unpublished until approved.
